Sprint 14 — What Changed
Symptoms Observed
  • 13 paper trades stuck in status='filled' for up to 16.5 days
  • Post-drain audit: 9 additional rows had fill_price=None — data integrity violation
Root Causes (three compounding)
  1. Kalshi taxonomy drift — API returned determined/finalized, matcher only accepted settled
  2. Silent exception swallowing — log.debug() hid stack traces, no Pushover fired
  3. Line 544 hardcoded None — _cancel_after() never parsed fill_price from API response (copy-paste bug)
Three-Layer Defense-in-Depth
Layer 1 Code fix — _cancel_after() now derives fill_price from (maker_cost + taker_cost) × 100 / fill_count ✓ LIVE
Layer 2 Application guard — update_paper_fill rejects corrupt writes, downgrades to unfilled (not stuck) ✓ LIVE
Layer 3 Schema CHECK constraint — deferred (SQLite no ADD CONSTRAINT; rebuild would block event loop) ⏸ QUEUED
Recovery
  • backfill_orphan_fills.py --apply recovered all 9 orphan rows from Kalshi API
  • Result: 6W / 3L, net −23¢ — close to breakeven, right-censored data salvaged
KEY DECISION · Semantic Correction
Collaborator recommended status='stuck' for corrupt rows. Pushed back → used status='unfilled'.

Rationale: stuck implies unobservable outcome of a known execution (right-censored, must recover). unfilled implies known non-execution (terminal). If fill_price is missing, no execution was ever recorded — unfilled is the only provable claim. Using stuck would waste reconciliation budget hunting for fills that likely don't exist.
